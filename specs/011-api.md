# API

## Overview

One HTTP surface under `/v1` on the public listener, one grammar for
every kind: apply by name, read by id or name, list, delete, and the
one verb a Key has. Every request body is a manifest
([[003-manifest-contract]]), every response body is JSON, and every
refusal is one envelope with one code and one fixed user sentence. This
spec owns that grammar, the addressing and the concurrency rules, the
usage and identity routes, the rate limit, and the error table, which
is the single table of every code the server can return on either
plane. The OpenAPI document is generated from the Go types and the
route table and served, so a generated client and the server agree by
construction rather than by review.

The grammar is small on purpose. Four kinds, four methods, one body
shape, one resolve. Everything a platform would want beyond it, roles,
teams, plans, a console, is the authorizer's and the platform's
([[001-architecture]], [[006-identity]]).

## Current state

Nothing is built. The repository holds the scaffold of
[[002-repository-scaffold]]: the binary serving its probes, typed
configuration, and the gate, on pkg v0.65.0.

## Design

### The grammar

Four routes per kind, identical for `Provider`, `Model`, `Key`, and
`Budget`:

| Method | Path | Does |
|---|---|---|
| `PUT` | `/v1/{kind}s/{name}` | apply: create when no object of that name exists, update when one does; `201` on create, `200` on update; the body is a manifest, or a manifest without `apiVersion`, `kind`, and `metadata.name`, which the route supplies through `Decode`'s hint ([[003-manifest-contract]]); the response is the object `Put` wrote its `id`, `version`, `createdAt`, and `updatedAt` back into ([[010-state]]), so no second read follows the write |
| `GET` | `/v1/{kind}s/{id-or-name}` | read one object with its `status` |
| `GET` | `/v1/{kind}s` | list, with the filters and paging below |
| `DELETE` | `/v1/{kind}s/{id-or-name}` | delete; `204` with no body |

Apply is create-or-update because that is what one schema and one
resolve produce: the body is a whole object, `Resolve` runs the same
six stages whether or not `Existing` is set, and the response is the
resolved object either way. A caller that does not know whether the
object exists does not have to.

Apply is by name and only by name. A `PUT` whose path segment carries
an id prefix, `PUT /v1/keys/key_01J9...`, is `invalid_field` at
`metadata.name`, because no name may begin with one
([[003-manifest-contract]]) and the path is the name: a caller that
holds an id reads the object, which returns its name, and applies
that. There is therefore no creating `POST` on this surface and
nothing for an `Idempotency-Key` to guard: a `PUT` repeated with one
body is `201` then `200` with the same object, which is idempotency by
construction, and `If-None-Match: *` is the create-once precondition
for a caller that must not update. The one `POST` that changes state,
`/v1/keys/{id-or-name}/rotate`, is not idempotent and takes no key: a
repeat is a second rotation, and a caller whose response was lost
rotates again and holds the last value returned.

The path is versioned, `/v1`, and the body is versioned,
`lux.latere.ai/v1beta1`, on two axes. Under `/v1` every change is
additive: a route, a query parameter, a response member, an error code
may be added and none is removed or changed in meaning, which is the
same promise the schema makes for its fields
([[003-manifest-contract]]). A change that cannot be additive is
`/v2`, served beside `/v1` for the period the CHANGELOG names, and is
independent of the manifest's `apiVersion`, which moves on its own
rule: a `/v1` route may serve a `lux.latere.ai/v2` body one day, and
`/v2` may still serve `v1beta1`.

There is no `PATCH`, in any mode. A partial body cannot go through
`Resolve`: stages 1 and 2 validate and default a whole object, stage 5
compares a whole object against `Existing`, and a merge would need a
second set of rules for absent versus null, for list members, and for
maps, living beside the schema and drifting from it. That is a second
meaning for a manifest, which invariant 1 of [[001-architecture]]
forbids. The loop is `GET`, edit, `PUT`, and it closes because `status`
in an applied manifest is ignored ([[003-manifest-contract]]), so the
body a `GET` returned re-applies unchanged. A `PATCH` on a route in the
table is `not_found`, the same answer [[004-request-path]] gives a
method the door table does not list.

### Addressing

An object is applied by name and addressed by either. `{id-or-name}` is
the kind's prefixed ULID (`prv_`, `mdl_`, `key_`, `bud_`) when it
carries that prefix and a name otherwise, resolved through
`Objects.Get` or `Objects.ByName` ([[010-state]]); the two never
collide because a name may not begin with a prefix
([[003-manifest-contract]]), and an id of another kind's prefix on a
route, `/v1/keys/prv_...`, is `not_found`. A body whose
`metadata.name` differs from the path is `invalid_field` at
`metadata.name`; a body with no `metadata.name` takes the path's.

`/v1/models` on this surface is the `Model` kind: the operator's and
the platform's view, bearer-authenticated, in the manifest shape. The
model list an SDK asks for, `GET /openai/v1/models`, `GET
/anthropic/v1/models`, `GET /gemini/v1beta/models`, and `GET
/lux/v1/models`, is a door route, Key-authenticated, in that dialect's
own list shape, and is [[004-request-path]]'s. The paths differ by the
door prefix, so the two never meet in this server; a platform that
mounts a door at its own origin's root, so that an SDK's default
`/v1/models` reaches it, chooses there which of the two answers that
path, and this spec takes no position on its choice.

A `Model` name may carry `/`, because a discovered Model is named
`<provider>/<upstream name>` and the upstream name may itself contain
`/` ([[003-manifest-contract]]). The model routes are therefore
`/v1/models/{name...}`, matching any number of segments, and the
handler unescapes each segment and rejoins them with `/`. Both
`/v1/models/openai%2Fgpt-5` and `/v1/models/openai/gpt-5` name the same
object, and `mdl_` ids always work; a rejoined name that fails 003's
name rule is `not_found`.

The other three kinds use `{name}`, one segment. Their names are
DNS-1123 labels, which cannot contain `/`, and `keys` carries a
subroute, so a trailing wildcard there would swallow `/rotate`. The
asymmetry is deliberate and is the only one.

### Concurrency

Every object response carries `ETag: "<version>"` and the same integer
in `status.version`, from the store's `version` for that row
([[010-state]]). `status.version` is rendered by the API and is not
part of the manifest a caller writes: like the rest of `status` it is
ignored on apply, so a read-modify-write round trip carries it back
harmlessly.

| Request header | Means | On a mismatch |
|---|---|---|
| `If-Match: "<version>"` | update this object at exactly this version | `conflict`, 409 |
| `If-Match: *` | the object must exist | `not_found`, 404 |
| `If-None-Match: *` | create only; the name must be free | `already_exists`, 409 |
| none | read-modify-write | retried, below |

A `PUT` without a precondition reads the current object, resolves
against it, and writes with the version it read; a `ErrVersionConflict`
from the store is retried up to three times before `conflict` is
returned, so a caller that does not care about concurrency does not see
one. A create whose name was taken between the read and the write is
`ErrNameTaken`, which is `already_exists`. `DELETE` accepts `If-Match`
with the same meaning. The only forms accepted are `*` and one
quoted decimal integer; a weak validator (`W/"7"`), a list, or anything
else is `invalid_field` at `If-Match` or `If-None-Match`, never a
silent match. The version is the row's and starts at `1` for every
row, so a name deleted and created again starts again at `1`; an
`ETag` held across a delete is a stale precondition like any other.

### The route table

Every route under `/v1` requires a bearer from a listed issuer
([[006-identity]]) and asks the authorizer the action in its row,
except the rows whose action is `none`: `/v1/self` and the tunnel
carrier are authenticated and authorize nothing, the carrier because
the session it joins was authorized at connect
([[013-tunnelled-runtimes]]); `/v1/openapi.json` and `/.well-known/lux`
need no bearer at all, because a document that describes the API
carries no installation's data; and `/internal/tunnel/{id}` is not
under `/v1`, takes `LUX_TUNNEL_FORWARD_SECRET`, and is on the internal
listener alone.

| Method | Path | Does | Action |
|---|---|---|---|
| `PUT` | `/v1/providers/{name}` | apply | `provider.create` or `provider.update` |
| `GET` | `/v1/providers` | list | `provider.list` |
| `GET` | `/v1/providers/{id-or-name}` | read, never with a credential value | `provider.read` |
| `DELETE` | `/v1/providers/{id-or-name}` | delete; `provider_in_use` while a declared Model targets it; its discovered Models go with it ([[005-providers]]) | `provider.delete` |
| `POST` | `/v1/providers/{id-or-name}/tunnel` | the tunnel session of a `tunnel: true` Provider ([[013-tunnelled-runtimes]]) | `provider.tunnel` |
| `POST` | `/v1/providers/{id-or-name}/tunnel/carry` | one carrier stream of an open session ([[013-tunnelled-runtimes]]) | none: the session is the authorization |
| `POST` | `/internal/tunnel/{id}` | internal listener only: one request forwarded from another replica, bearer `LUX_TUNNEL_FORWARD_SECRET` ([[013-tunnelled-runtimes]]) | none |
| `PUT` | `/v1/models/{name...}` | apply a declared Model, replacing a discovered one of that name | `model.create` or `model.update` |
| `GET` | `/v1/models` | list; `?source=declared\|discovered`, `?provider=` | `model.list` |
| `GET` | `/v1/models/{name...}` | read | `model.read` |
| `DELETE` | `/v1/models/{name...}` | delete; a declared Model's deletion lets discovery restore the discovered one | `model.delete` |
| `PUT` | `/v1/keys/{name}` | apply; a create returns `status.value` once, unless the body supplied `spec.value` ([[007-keys-and-limits]]), in which case the response carries neither `spec.value` nor `status.value` and `status.prefix` is the `sup_` handle | `key.create` or `key.update` |
| `GET` | `/v1/keys` | list, never with a value | `key.list` |
| `GET` | `/v1/keys/{id-or-name}` | read with `status.usage` | `key.read` |
| `DELETE` | `/v1/keys/{id-or-name}` | delete; the hash is removed in the same transaction | `key.delete` |
| `POST` | `/v1/keys/{id-or-name}/rotate` | mint a new value, keep the id, name, spec, owner, and windows; `200` with `status.value` | `key.update` |
| `PUT` | `/v1/budgets/{name}` | apply | `budget.create` or `budget.update` |
| `GET` | `/v1/budgets` | list | `budget.list` |
| `GET` | `/v1/budgets/{id-or-name}` | read with `status.spent` and `status.resetsAt` | `budget.read` |
| `DELETE` | `/v1/budgets/{id-or-name}` | delete; `budget_in_use` while a Key names it ([[007-keys-and-limits]]) | `budget.delete` |
| `GET` | `/v1/usage` | aggregates, `{"items": [rows]}`; the parameters and the row shape are [[009-usage-and-metering]]'s | `usage.read` |
| `GET` | `/v1/requests` | records, newest first, `{"items": [records], "next_cursor": "...", "source": "archive\|memory"}`; the parameters, the record, `source`, and the `limit` cap of 1000 are [[009-usage-and-metering]]'s | `usage.read` |
| `GET` | `/v1/self` | the caller's identity and what this server holds for it, below | none |
| `GET` | `/v1/openapi.json` | the served OpenAPI document; no bearer | none |
| `GET` | `/.well-known/lux` | the server's identity, below; no bearer | none |

The handler order on every item route is read, authorize, act: load the
object by id or name, build the authorizer's `resource` from what was
loaded, ask, then act. A missing object is `not_found`; a deny on the
request's own action is `forbidden`; a deny reached through `Lookup`
during `Resolve` is `not_found` ([[006-identity]]). `?owner=` and every
other list selector is intersected with the authorizer's `filter`, so a
selector outside the filter is an empty list and never a 403.

`GET /v1/self` asks no action, because asking permission to see the
identity the caller just presented is a category error: the response
carries what the caller sent and what this server was already told
about it.

```json
{
  "subject": "https://login.example.com|alice",
  "issuer": "https://login.example.com",
  "sub": "alice",
  "claims": {"email": "alice@example.com", "name": "Alice", "groups": ["research"]},
  "policy": "authorizer",
  "limits": {"requests_per_minute": 1200, "max_key_spend": "50"},
  "filter": {"owners": ["https://login.example.com|alice"]}
}
```

`policy` is `authorizer`, `owner`, or `file`. `limits` and `filter` are what
this replica's decision cache holds for the subject
([[006-identity]]) and are absent until a decision has been made for
it, which the field's documentation says; they are a report of what was
granted, never a grant.

`GET /.well-known/lux` is the one document a client reads before it has
a token, so a command, a platform's front, and the conformance suite
configure themselves from one fetch:

```json
{
  "name": "lux",
  "version": "0.1.0",
  "apiVersion": "lux.latere.ai/v1beta1",
  "api": "https://lux.example.com/v1",
  "openapi": "https://lux.example.com/v1/openapi.json",
  "doors": {
    "openai": "https://lux.example.com/openai",
    "anthropic": "https://lux.example.com/anthropic",
    "gemini": "https://lux.example.com/gemini",
    "lux": "https://lux.example.com/lux"
  },
  "dialects": ["openai", "anthropic", "gemini", "lux"],
  "issuers": ["https://login.example.com"],
  "audience": "lux",
  "mode": "server"
}
```

Every URL is built from `LUX_PUBLIC_URL`. `mode` is `server` or
`file`. The document names the build and the issuers and nothing else;
an issuer URL is public by definition, and the version of an open
source gateway is not a secret an installation can keep.

### The lifecycle of an apply

```mermaid
sequenceDiagram
  participant C as caller
  participant A as /v1 handler
  participant I as identity
  participant Z as authorizer
  participant M as manifest.Resolve
  participant S as store
  participant J as journal
  C->>A: PUT /v1/keys/run-42, If-Match "7"
  A->>A: request id, rate bucket, body limit
  A->>I: verify the bearer against the issuers
  I-->>A: subject, claims
  A->>S: ByName(Key, run-42)
  S-->>A: the object and version 7
  A->>Z: key.update on the loaded object
  Z-->>A: allow, limits
  A->>M: Decode, then Resolve with Actor, Lookup, Defaults, Limits, Existing
  M->>Z: model.use per selector, budget.draw
  Z-->>M: allow or deny; a deny is not_found
  M-->>A: the resolved object and its warnings
  A->>S: Put(obj, ifVersion 7) and the journal row, one transaction
  S->>J: key.updated
  S-->>A: version 8
  A-->>C: 200, the resolved object, ETag "8", Lux-Request-Id
```

A refusal at any step is the envelope below, and nothing after it runs.
The authorizer is asked before `Resolve` for the request's own action
and during `Resolve` for the references, which is why a manifest naming
a Budget the caller may not draw is `not_found` on the field rather
than `forbidden` on the request.

### Assembling Resolve

`manifest.Options` ([[003-manifest-contract]]) is built per request:

| Field | From |
|---|---|
| `Actor.Subject` | the rendered subject of the verified bearer ([[006-identity]]) |
| `Lookup` | the store and the authorizer's decision cache, asking `provider.read` per target, `budget.draw`, and `model.use` per selector, the last never cached because a selector is not an id ([[006-identity]]), mapping a deny to `not_found` and an unavailability to `authorizer_unavailable` |
| `Defaults` | `LUX_DEFAULT_REQUESTS_PER_MINUTE`, `LUX_DEFAULT_TOKENS_PER_MINUTE`, `LUX_UPSTREAM_TIMEOUT` |
| `Limits` | the `limits` of the decision on the request's own action ([[006-identity]]) |
| `Existing` | the object loaded by name, `nil` on a create |
| `FileMode` | false; the file mode never applies through the API ([[010-state]]) |
| `AllowPrivateUpstreams` | `LUX_UPSTREAM_ALLOW_PRIVATE` |
| `PublicURL` | `LUX_PUBLIC_URL` |
| `Now`, `NewName` | the clock and the API's name generator |

`max_keys` from the decision is checked at `key.create` in the same
transaction as the write, and a create over it is `ceiling_exceeded`
([[006-identity]]). The response is the resolved object with the
stored status merged in, which is what [[001-architecture]]'s
`TestAPIAndImporterResolveAgree` compares against `Resolve`'s own
output.

### Bodies, types, and limits

A request body is a manifest in one of the content types
[[003-manifest-contract]] decodes: `application/json`,
`application/yaml`, `application/x-yaml`, `text/yaml`. Anything else is
`unsupported_media_type`. A body above `LUX_MAX_MANIFEST_BYTES`
(default `65536`) is `body_too_large`, read no further; the data plane
has its own, larger limit ([[004-request-path]]).

Every response body is JSON, in the Go struct order the OpenAPI
document records. There is no content negotiation: a manifest is
written in YAML by people and read back by programs, and the `lux`
command renders YAML locally from the JSON it received
([[014-agent-client]]), so a second encoder on the server would buy one
convenience at the cost of a second golden corpus and a second set of
round-trip tests.

A list response is `{"items": [...], "next_cursor": "<cursor>"}`, with
`next_cursor` absent on the last page. The member is spelled as the API
grammar below spells it, so a client written for one surface pages every
other the same way.

### Lists

| Parameter | Kinds | Rule |
|---|---|---|
| `label` | every | `k=v`, repeatable; every pair must match |
| `owner` | every | a rendered subject; intersected with the authorizer's `filter` |
| `source` | models | `declared` or `discovered` |
| `provider` | models | a Provider name or `prv_` id; Models with a target on it |
| `limit` | every | default `50`, at most `200`; above is `invalid_field` |
| `cursor` | every | the previous response's `next_cursor`, opaque |

The parameters map onto `Objects.List`'s `Filter` and `Page`
([[010-state]]). A cursor is the store's, opaque to the caller, and
valid only for the kind and filter that produced it; anything else is
`invalid_field` at `cursor`. A query parameter no route defines is
`invalid_field` at that parameter's name, the same strictness the
manifest has for a field, so a misspelt filter is a refusal and not a
silently wider list. A list never returns an object the authorizer's
`filter` excludes, and never returns a Key's value or a Provider's
credential.

### The usage routes

`GET /v1/usage` and `GET /v1/requests` are this spec's routes over
[[009-usage-and-metering]]'s parameters, rows, and records; the seam
between the two is exact:

- The route parses the parameters as that spec defines them, refusing
  a bad one with `invalid_field` at its name, and builds
  `metering.Query` or `metering.RecordQuery`.
- The `key`, `model`, and `provider` parameters take a name or an id;
  the route resolves each name to its id through `Objects.ByName`
  before the query and before the authorizer, so `Query.Keys`,
  `.Models`, `.Providers` carry ids alone and the `usage.read`
  resource of [[006-identity]] carries `keys` as ids and `owners` as
  rendered subjects. A name that resolves to nothing is an empty
  result, never `not_found`, for the same reason a filter outside the
  authorizer's is.
- The authorizer's `filter` is intersected with the query: `owners`
  narrows `Query.Owners`, `labels` narrows `Query.Labels`; an
  intersection that is empty is an empty `items`, never a 403.
- `/v1/usage` is not paged: it answers `{"items": [rows]}` and the 90
  day range bound is what keeps the row count finite. `/v1/requests`
  pages by `cursor` and `next_cursor` as a list does, with the `limit`
  default `50` and cap `1000` that spec sets, and carries `source`
  beside `items`.

### The file mode

With `LUX_MANIFEST_DIR` set, desired state is the directory and no
caller can change it ([[010-state]]). The whole of `/v1`, the kinds,
the usage routes, `/v1/self`, and `/v1/openapi.json`, is mounted on the
internal listener and not on the public one, and needs no bearer,
because there is no issuer to require and nothing to authorize
([[006-identity]]); `/v1/*` on the public listener is `not_found`, the
answer of any path that is not mounted, and `/.well-known/lux` stays
on the public listener with `"mode": "file"`. Every `PUT`, `POST`, and
`DELETE` under `/v1/{kind}s`, the tunnel session and carrier included,
is `read_only`, 405, with `Allow: GET` and the developer detail naming
the directory; the refusal is before the body is read and before any
decode, so a large or malformed body in this mode costs nothing.
`PATCH` is `not_found` here as in every mode, because it is not a
route. `GET /v1/self` answers `"policy": "file"` with no subject, since
no bearer was presented. The read routes, `/v1/usage`, and
`/v1/requests` are served normally.

### The error table

The envelope is `latere.ai/x/pkg/httpjson`'s `ErrorEnvelope`, written
through `httpjson.WriteError`: one member `error` carrying `code`,
`message`, and `details`, the last a map. `details` always carries
`request_id`; it carries `paths`, a list of JSON paths, for a code that
names fields, and `detail`, one developer sentence, where there is one
to give. `message` is the fixed user sentence below and is never built
from an underlying error, an authorizer's `reason`, or an upstream's
body.

```json
{"error": {"code": "invalid_field", "message": "A field has a value it cannot take.",
           "details": {"request_id": "req_01J9...", "paths": ["spec.baseURL"],
                       "detail": "a loopback host needs LUX_UPSTREAM_ALLOW_PRIVATE"}}}
```

The table is both planes' in one place, because one code means one
thing whichever surface raised it and a caller that sees
`rate_limited` on a door and on `/v1` should read one sentence.
[[004-request-path]] renders these codes into each door's own shape;
the code, the status, and the sentence are the same. The table's scope
is every code a handler writes in an HTTP response on either plane.
Three groups of names are codes in their own specs and are not rows
here, because no response ever carries them as its error:
`client_closed`, the `error` a usage record carries when the caller
went away ([[004-request-path]], [[009-usage-and-metering]]); the
tunnel session's close reasons `superseded`, `token_expired`,
`provider_deleted`, `draining`, which travel in a frame
([[013-tunnelled-runtimes]]); and the `lux` command's own exit codes
([[014-agent-client]]).

| `model_not_found` | 404 | There is no model of that name. | [[004-request-path]] |
| `read_only` | 405 | This server reads its manifests from a directory and cannot change them. | [[010-state]] |
| `already_exists` | 409 | An object of this kind already has that name. | this spec |
| `conflict` | 409 | The object changed since you read it; read it again and retry. | this spec, [[010-state]] |
| `immutable_field` | 409 | This field cannot be changed after the object is created. | [[003-manifest-contract]], [[007-keys-and-limits]] |
| `budget_in_use` | 409 | Keys still draw from this budget. | [[007-keys-and-limits]] |
| `provider_in_use` | 409 | Models still target this provider. | [[005-providers]] |
| `body_too_large` | 413 | The request body is larger than this server accepts. | [[004-request-path]], this spec |
| `unsupported_media_type` | 415 | Send the manifest as JSON or YAML. | [[003-manifest-contract]] |
| `ceiling_exceeded` | 422 | The value is above what you may ask for. | [[006-identity]], [[003-manifest-contract]] |
| `rate_limited` | 429 | Too many requests; wait and retry. | this spec, [[007-keys-and-limits]] |
| `spend_exceeded` | 429 | This key has spent its limit for the window. | [[007-keys-and-limits]] |
| `budget_exhausted` | 429 | The budget has nothing left for the window. | [[007-keys-and-limits]] |
| `internal` | 500 | Something went wrong on this server. | this spec |
| `upstream_error` | 502 | The provider returned an error. | [[004-request-path]] |
| `authorizer_unavailable` | 503 | The permission service is unavailable; retry shortly. | [[006-identity]] |
| `store_unavailable` | 503 | This server cannot reach its store; retry shortly. | this spec, [[010-state]], [[004-request-path]] |
| `provider_unavailable` | 503 | No provider for this model is available right now. | [[004-request-path]] |
| `upstream_timeout` | 504 | The provider did not answer in time. | [[004-request-path]] |

`internal` is the only code with no cause in another spec: it is what a
handler returns when it has a bug, and its `detail` is empty because a
caller learns nothing useful from a panic. `store_unavailable` is any
store error that is not `ErrNotFound`, `ErrVersionConflict`,
`ErrNameTaken`, `ErrHashTaken`, `ErrInvalidCursor`, or `ErrReadOnly`
([[010-state]]), including one `Resolve` passes through from its
`Lookup` as a plain error ([[003-manifest-contract]]); `ErrInvalidCursor` is `invalid_field` at `cursor`, and
`ErrHashTaken` is `invalid_field` at `spec.value` with a detail that
names no Key ([[007-keys-and-limits]]).

`TestErrorTable` reads every spec in this deck, collects every code
named in an error table, the `Code` column of [[003-manifest-contract]]'s
and [[004-request-path]]'s tables and every backticked
`snake_case` word a spec says a request is "refused with" or
"answers", subtracts the three groups above, and asserts that each has
exactly one row here with a status and a sentence, that a code in
[[004-request-path]]'s table has the same status there, that no two
rows share a sentence, that every sentence is one sentence in the user
register, and that no handler on either plane writes a `message`
outside the table.

### Request ids

Every request has one, `req_` and a ULID, on every response in
`Lux-Request-Id`, in `details.request_id` of every error, in the
`request.id` the authorizer sees ([[006-identity]]), in the event's
`request_id` ([[012-request-log-and-events]]), on the usage record
([[009-usage-and-metering]]), and on the trace
([[019-observability]]). A caller's own `Lux-Request-Id` is ignored and
replaced, on both planes and for the same reason
([[004-request-path]]): an identifier a caller chooses is an identifier
a caller can reuse, and every one of the five places above assumes it
is unique.

A caller's `X-Request-Id`, when present, is echoed unchanged on the
response of both planes and used for nothing else: not as the record's
id, not in a log line, not toward a provider. It is a correlation
handle for the caller's own tracing, which is what the API grammar below
asks a surface to echo, and echoing it costs the server no assumption. A
value longer than 128 bytes or carrying a byte outside printable ASCII
is dropped rather than echoed, so a header cannot be used to smuggle
bytes into a response.

### Rate limits

After authentication, `LUX_REQUESTS_PER_MINUTE` per subject, which the
authorizer's `limits.requests_per_minute` overrides for that subject
([[006-identity]]); a token bucket per replica with the limit as the
burst, through `latere.ai/x/pkg/ratelimit`; `0` is no limit. Before
authentication, one bucket per client address of
`LUX_UNAUTHENTICATED_REQUESTS_PER_MINUTE`, which bounds a flood of bad
tokens and, on the doors, of guessed Key values
([[007-keys-and-limits]]). Both are per replica, so an installation
admits the configured rate times its replica count, exactly as the data
plane's do ([[009-usage-and-metering]]). The client address is the
peer's, or, when the peer is in `LUX_TRUSTED_PROXIES`, the last
`X-Forwarded-For` entry outside those ranges, so a gateway deployed
behind a platform's API layer limits per caller and not per proxy; a
forwarded header from any other peer is ignored, and the same address
is the authorizer's `request.ip` ([[006-identity]]). The bucket and the
address rule run in `internal/serve` before the door handler of
[[004-request-path]], which takes the address as a value and reads no
header for it.

Every `/v1` response carries `RateLimit-Limit`, `RateLimit-Remaining`,
and `RateLimit-Reset`; a `rate_limited` response adds `Retry-After` in
seconds.

### CORS

No `Access-Control-*` header is written on either plane, and an
`OPTIONS` request is `not_found`. The doors and `/v1` are API surfaces
for SDKs and for server-side callers, and the credential either takes,
a Key or an issuer token, is one a browser page should not hold. A
platform that wants a console puts it in front of this API with its own
origin, its own session, and its own CORS policy, which is the same
boundary every other platform concern sits on
([[020-building-a-plane]]).

### The API grammar

A platform that routes this surface under its own origin by path
prefix meets it with the grammar that origin holds every service to:
one bearer header, one error envelope, `limit` and `cursor` in and
`next_cursor` out, `/v1` additive, `Idempotency-Key` on a creating
`POST`, opaque identifiers, `429` with `Retry-After` and the
`RateLimit-*` headers, `X-Request-Id` echoed, and an OpenAPI document
published from code. This spec follows each rule where the core can
without learning a platform's name, and states its one deviation and
its two refinements so the platform's conformance test reads a decision
rather than a gap:

| Rule | Here |
|---|---|
| bearer | `Authorization: Bearer` on `/v1`; the audience is `LUX_OIDC_AUDIENCE` and a platform sets it to its own ([[006-identity]]) |
| envelope | `httpjson.ErrorEnvelope`, above, with the developer detail in `details.detail`; a `manifest.Error` maps as `Code.Message()` to `message`, `Paths` to `details.paths`, and `Detail` to `details.detail` ([[003-manifest-contract]]) |
| pagination | `limit`, `cursor`, `next_cursor`, opaque, above |
| versioning | `/v1` additive, above |
| idempotency | no creating `POST` exists; `PUT` by name is idempotent by construction, above. This is the deviation: the grammar's header has no route to apply to, and `POST .../rotate` is a mutation whose repeat is a second rotation |
| identifiers | prefixed ULIDs, opaque to a caller beyond the prefix. The grammar's owner spellings `me`, `org`, `u-<id>` are a platform's; here an owner is the rendered subject of [[006-identity]], and a platform renders it as it likes. This is the first refinement |
| limits | `429`, `Retry-After`, `RateLimit-Limit`, `RateLimit-Remaining`, `RateLimit-Reset`, below |
| tracing | `X-Request-Id` echoed, above; `Lux-Request-Id` is the server's own id beside it. This is the second refinement: the grammar's echo is honoured and the record's id stays the server's |
| reference | `api/openapi.yaml` from code, served at `GET /v1/openapi.json`, below |

The doors are outside the grammar by design: they speak each
provider's dialect verbatim so a third-party SDK drops in, which is the
exception the grammar itself makes for the compatibility dialects, and
[[004-request-path]] owns their shapes.

### The listeners

The public listener serves the four doors, `/v1`, `/.well-known/lux`,
and the three probes that a release smoke reaches through an ingress.
The internal listener serves the probes and `/metrics`
([[019-observability]]) and no `/v1`, except in the file mode, where
`/v1` is the internal listener's alone. `/metrics` is never on the
public listener ([[002-repository-scaffold]]).

### OpenAPI

The kinds' Go types carry no `apiVersion` or `kind` field, since
`MarshalJSON` writes both ([[003-manifest-contract]]); the generator
adds the two members to every kind's schema itself.

`tools/apidoc` generates `api/openapi.yaml` from the types of
`manifest/v1`, the route table above, and the error table above. The
document is embedded and served as JSON at `GET /v1/openapi.json`,
converted from the committed YAML at build time, so there is one source
and not two. The gate fails when the committed document differs from a
fresh generation, which makes a route or a field added without
regenerating a red build rather than a silent drift. The conformance
suite validates every response it receives against the document
([[018-conformance-suite]]).

### Configuration

| Variable | Required | Default | Purpose |
|---|---|---|---|
| `LUX_REQUESTS_PER_MINUTE` | no | `600` | control plane requests one subject may send in a minute, per replica; `0` is no limit |
| `LUX_UNAUTHENTICATED_REQUESTS_PER_MINUTE` | no | `60` | requests one client address may send before authentication, per replica, on both planes |
| `LUX_TRUSTED_PROXIES` | no | unset | comma separated CIDR ranges of the proxies in front of the gateway; when the peer is in one, the client address is the last `X-Forwarded-For` entry outside every range; unset trusts no header, and the peer is the client |
| `LUX_MAX_MANIFEST_BYTES` | no | `65536` | the largest control plane request body accepted |
